# Patients and Admissions modules — design

Date: 2026-11-23
Status: approved (pending builder check)

## Intent

The database schema in [db/init.sql](../../../db/init.sql) already defines `patients` and
`admissions`, and the seed data populates both. The backend has no code for either table: the
only artifact is an incomplete, untracked stub at
`backend/src/main/java/com/sio/backend/entity/Patients.java` that maps three of the eleven
columns.

Goal: expose both tables through the backend with the same component set and conventions the
existing modules use, then regenerate the frontend OpenAPI client so the new endpoints are
consumable from Angular.

## Why now

The frontend already has a `lista-pz` (patient list) feature and an `accettazione` (admission)
feature, both currently backed by placeholder data. The lookup dictionaries
(`triage_colors`, `arrival_modes`, `pathologies`) are already exposed; patients and admissions
are the missing half of the domain.

## Goals

- Full backend module for `patients`: entity, DTO, mapper, repository, service, controller.
- Full backend module for `admissions`: entity, status enum, request/response DTOs, mapper,
  repository, service, controller.
- Endpoints follow the existing conventions: `ApiResponse` wrapper, Swagger annotations,
  paginated variants where the existing modules have them, `GlobalExceptionHandler` for errors.
- Regenerate the frontend OpenAPI client from the live spec and fix the one consumer that
  breaks.

## Non-goals

- No authentication or authorization. The `users` table stays unmapped.
- No changes to `db/init.sql`. The schema is the source of truth and is already correct.
- No new frontend features. The generated client is regenerated; `lista-pz` and `accettazione`
  keep their current placeholder behavior.
- No Flyway/Liquibase. `ddl-auto` stays `none`.
- No changes to the existing `pathologies`, `triage_colors`, `arrival_modes` modules.

## Anti-goals

- A module that compiles but cannot read the seeded rows (wrong enum mapping, wrong schema
  qualification).
- Diverging from the repo's package-by-layer layout.
- Hand-editing generated client files.

## Constraints

- Java 25, Spring Boot 4.1.2, Maven wrapper (`backend/mvnw.cmd`).
- `JAVA_HOME` currently points at `C:\Program Files\Java\jdk-25.0.2`, which does not exist.
  The real JDK is `C:\Program Files\Java\jdk-25.0.5.1`. Builds must set `JAVA_HOME` explicitly.
- PostgreSQL 16 on `localhost:5434`, database `sio_db`, schema `sio`, seeded by
  `db/init.sql`. The container `sio_postgres` is running.
- `spring.jpa.hibernate.ddl-auto: none` — Hibernate never creates or alters tables.
- Existing entities qualify the schema with `@Table(name = "...", schema = "sio")`.
- The frontend client is generated by `@openapitools/openapi-generator-cli` 7.27.0, pinned in
  `frontend/openapitools.json`. It is not installed in `node_modules` yet.

## Approaches considered

### 1. Package-by-layer, full modules, clean client regeneration (chosen)

Entities in `entity/`, DTOs in `dto/`, mappers in `mapper/`, repositories in `repository/`,
services in `service/`, controllers in `controller/`. Endpoints under `/api/patients` and
`/api/admissions`. Delete `frontend/src/app/core/api/` and regenerate from the live
`/api-docs`.

Matches every existing module. Cost: a large diff in the generated client, and the generated
service class names change.

### 2. Package-by-feature

`patients/` and `admissions/` packages holding all six component types each. This is what the
`upstream/patient-management` branch does.

Rejected: it contradicts the layout the rest of this repository uses, and the architecture
document (`backend/docs/DOC.md`) describes the layer-based structure.

### 3. Patients only, minimal CRUD

Rejected by the user's scope decision.

## Decisions

### API shape for admissions

The domain is emergency-department triage, not generic CRUD. The chosen surface:

| Method | Path | Purpose |
|---|---|---|
| GET | `/api/admissions` | Active admissions (stato != DIM), ordered by triage priority then arrival time |
| GET | `/api/admissions/{id}` | One admission with patient and dictionaries resolved |
| GET | `/api/admissions/braccialetto/{code}` | One admission by wristband code |
| POST | `/api/admissions` | Accept a patient: upsert the patient record, then create the admission |
| PATCH | `/api/admissions/{id}/stato` | Change clinical state; setting DIM stamps `data_ora_dimissione` |

Rationale: a plain CRUD surface cannot express "accept a patient" (which must upsert the
patient and reject a second open episode) or "advance the state" (which must stamp the
discharge timestamp). The state machine is `ATT -> VIS -> OBI | RIC -> DIM`.

### API shape for patients

| Method | Path | Purpose |
|---|---|---|
| GET | `/api/patients` | All patients, ordered by surname then name |
| GET | `/api/patients/paginated` | Paginated patients |
| GET | `/api/patients/{id}` | One patient |
| GET | `/api/patients/search?cf=...` | One patient by fiscal code, case-insensitive |
| POST | `/api/patients` | Create |
| PUT | `/api/patients/{id}` | Update |
| DELETE | `/api/patients/{id}` | Delete |

The list and paginated pair mirrors `pathologies`, `triage_colors` and `arrival_modes`.

### Enums

`PatientSex` (`M`, `F`) and `AdmissionStatus` (`ATT`, `VIS`, `OBI`, `RIC`, `DIM`) are Java
enums, mapped to the PostgreSQL enum types with `@JdbcTypeCode(SqlTypes.NAMED_ENUM)` and
`@Enumerated(EnumType.STRING)`. Typed enums give validation and Swagger documentation for
free; `String` would silently accept invalid values.

### Entity naming

The patient entity stays `Patients` (plural), matching the existing stub and the
`Pathologies` convention. The admission entity is `Admission` (singular), matching
`TriageColor` and `ArrivalMode`.

### Frontend client regeneration

Delete `frontend/src/app/core/api/` and regenerate from `http://localhost:3000/api-docs` with
the pinned generator version. The current directory contains two overlapping services
(`gestioneRisorseSIO.service.ts` and `resourcesController.service.ts`) generated from
different tag sets; a clean regeneration removes the duplication.

One consumer breaks: `frontend/src/app/core/resources/resources.ts` injects
`GestioneRisorseSIOService`. It must be updated to the regenerated service class name.

## Business rules

1. **Accept a patient** (`POST /api/admissions`) runs in one transaction:
   - Upsert the patient on `codice_fiscale` (case-insensitive). Existing rows are updated with
     the submitted demographics.
   - Reject with `IllegalArgumentException` (HTTP 400) if the patient already has an admission
     whose `stato` is not `DIM`.
   - Resolve `patologia_code`, `codice_colore`, `modalita_arrivo_code` against the dictionaries;
     a missing code raises `EntityNotFoundException` (HTTP 404).
   - Generate a unique `braccialetto` in the seeded format `YYYY-NNNN`.
   - Persist with `stato = ATT`.
2. **Change state** (`PATCH /api/admissions/{id}/stato`) sets `stato`. When the new state is
   `DIM` and `data_ora_dimissione` is null, stamp it with the current time.
3. **Active list** excludes `DIM` and orders by `codice_colore.priority` ascending, then
   `data_ora_ingresso` ascending. Admissions with a null `codice_colore` sort last.
4. **Fiscal code** is normalized to uppercase and trimmed on write.

## Error handling

No new exception types. The existing `GlobalExceptionHandler` already maps
`IllegalArgumentException` to 400, `EntityNotFoundException` and `NoSuchElementException` to
404, and everything else to 500. Services throw those types.

## Validation

DTOs carry Jakarta validation annotations, matching the existing DTOs:

- `PatientsDTO`: fiscal code exactly 16 characters and not blank; name and surname not blank,
  max 100; birth date not null and not in the future; sex not null; address fields bounded.
- `AdmissionRequestDTO`: nested `PatientsDTO` marked `@Valid`; the three dictionary codes not
  blank and bounded; `noteTriage` free text.

## Verification

1. `backend/mvnw.cmd -q clean package` with `JAVA_HOME` set to the real JDK 25 path.
2. Start the app against the running `sio_postgres` container.
3. `GET /api/patients` returns the 7 seeded patients.
4. `GET /api/admissions` returns the 6 non-dismissed seeded admissions, ordered by triage
   priority.
5. `POST /api/admissions` with a new fiscal code creates the patient and the admission.
6. `POST /api/admissions` for a patient with an open episode returns 400.
7. `PATCH /api/admissions/{id}/stato?stato=DIM` stamps `data_ora_dimissione`.
8. `GET /api-docs` includes the new paths.
9. Regenerate the frontend client; `npm run build` in `frontend/` succeeds.

## Left to the builder

- Logging statements, following the `@Slf4j` + `log.debug` pattern of the existing services.
- Whether to keep the `audit/` package pattern (the existing `PathologiesAudit` is an empty
  class; no audit class is added for the new modules).
